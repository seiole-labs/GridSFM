# GridSFM combined benchmark summary

## Executive view

This report combines two local GridSFM-Open v1.1 evaluations:

- **Training-scale / in-distribution-style:** 25 accepted mixed-perturbation scenarios across five US-derived topologies, ranging from 651 to 1,271 buses.
- **Topology-and-scale OOD:** four accepted unmodified PGLib base cases, ranging from 6,470 to 20,758 buses.
- **Exploratory scale probes:** `case24464_goc` and `case78484_epigrids`, kept outside accepted aggregates because the 24k round-trip gate failed and the 78k round-trip was skipped.

“In-distribution” is shorthand here. The US-derived cases are within GridSFM-Open's stated training-size envelope and use a familiar source family, but exact scenario-level membership in pretraining is not publicly proven. The PGLib cases test topology and scale shift, not source-family shift, because PGLib/OPFData were represented during pretraining.

![Bus count versus AC-OPF and GridSFM timing](benchmark/plots/bus_count_vs_runtime.png)

The figure averages the five in-distribution perturbation runs for each topology/bus count and shows one-standard-deviation error bars. It also includes the four accepted OOD grids and two exploratory OOD probes. Solid segments connect accepted measurements; dashed segments continue through the exploratory probes as a visual interpolation guide, not a fitted scaling law. The figure is generated by `benchmark/plot_bus_timing.py`; the overview uses logarithmic axes so both training-scale and 78k-bus measurements remain visible.

These are component timings, not complete wall-clock measurements. The AC timer excludes process/container startup, MATPOWER parsing, export construction, serialization, file writing, and any round-trip solve. The GridSFM request timer excludes Python startup, imports, checkpoint loading, prediction serialization, and file writing. Consequently, ratios between these columns are descriptive rather than formal end-to-end speedups.

### Exact timing boundaries

The prediction JSON calls its request measurement `end_to_end_seconds`, but it is only end-to-end within a **model-resident inference request**. A complete cold-process end-to-end time is not currently recorded for either method.

| Recorded field | Timer starts | Timer stops | Included | Excluded |
|---|---|---|---|---|
| GridSFM `forward_seconds` | Immediately before `model(batch)` | Immediately after the forward pass and device synchronization | Neural inference, DC prior, predicted branch-flow calculation, feasibility head | Python startup/imports, checkpoint load, JSON parsing, feature preparation, batching, tensor-to-list conversion, serialization, output writing |
| GridSFM `end_to_end_seconds` | Before loading the `.pyg.json` | After output tensors are detached and moved to CPU | Input loading, PyG conversion, cycle/positional feature preparation, batching, device transfer, forward pass, CPU tensor return | Python startup/imports, checkpoint load, tensor-to-list conversion, prediction serialization, output writing |
| AC-OPF `solve_time_seconds` | Before `PowerModels.instantiate_model` | After `PowerModels.optimize_model!` returns | PowerModels/JuMP model construction, Ipopt initialization and optimization, solver-result construction | Julia/container startup, MATPOWER parsing, PyG export construction, serialization, file writing, and every separate validation re-solve |
| Cold process end-to-end | Not currently measured | Not currently measured | — | No defensible cold end-to-end value is available yet |

**AC-OPF timing is one solve, never the sum of two solves.** Where a source solve and a PyG round-trip re-solve were both performed, the benchmark table reports only the source solve's `solve_time_seconds`. The round-trip duration is stored separately in its audit JSON and is not added to the reported AC-OPF time. For example, the 24k row reports the source solve's 1,914.41 seconds, not source plus re-solve; the 78k direct comparison reports its single successful reference solve's 1,924.45 seconds and had no round-trip re-solve.

## Accepted OOD cases

| Case | Buses | Cost MAPE | V MAE | Angle MAE | Active KCL MAE | Overloaded branches | GridSFM request |

| `case6470_rte` | 6,470 | 2.604% | 0.02230 pu | 1.328° | 0.66549 pu | 182 / 9,005 (2.02%) | 14.91 s |
| `case8387_pegase` | 8,387 | 228.950% | 0.05137 pu | 54.735° | 1.30450 pu | 2,071 / 14,561 (14.22%) | 22.57 s |
| `case13659_pegase` | 13,659 | 6.624% | 0.04761 pu | 41.811° | 2.04792 pu | 76 / 20,467 (0.37%) | 25.47 s |

Performance is not monotonic with bus count. The 6,470-bus reference has the best accepted OOD cost and angle accuracy, the 8,387-bus PEGASE case is the strongest failure, and the 20,758-bus case has the best accepted OOD active-KCL MAE and branch-flow errors.

| Case | Gate status | Cost MAPE | V MAE | Angle MAE | Active KCL MAE | Overloaded branches | GridSFM request |

| `case24464_goc` | Round-trip failed: `0.11607 > 0.001` | 34.905% | 0.10262 pu | 60.158° | 0.06555 pu | 86 / 37,816 (0.23%) | 46.13 s |
| `case78484_epigrids` | Round-trip skipped; structural validation passed | 15.386% | 0.07506 pu | 93.442° | 0.06614 pu | 543 / 126,015 (0.43%) | 159.35 s |

The 78k result demonstrates execution capacity on CPU at roughly 16.84 times GridSFM-Open's stated training-size maximum. It is not an accepted accuracy result. Six inactive type-4 buses omitted from the PowerModels result were aligned with their parsed source states before inference, and the user chose to skip the PyG re-solve gate.

## Summarized interpretation

1. **The distribution shift is visible.** Relative to the training-scale set, accepted OOD voltage error is about 7.7× higher, angle error about 13.8× higher, and active-KCL MAE about 18.2× higher on average.
2. **Averages alone are misleading.** The 8,387-bus PEGASE case drives the accepted OOD cost mean from a median of 12.73% to 64.25% and similarly inflates Pg error.
3. **Larger does not automatically mean worse.** The 20,758-bus EpiGrids case is much better on active KCL and branch flows than the smaller PEGASE cases, despite its larger graph.
4. **Regression accuracy is not feasibility.** Both groups contain raw GridSFM predictions with KCL residuals and thermal overloads; predicted cost alone is insufficient to call a dispatch operationally valid.
5. **The model scales farther than its accepted benchmark envelope.** CPU inference completed at 24k and 78k buses, but those runs remain exploratory because conversion-integrity acceptance was not established.
6. **Timing claims need matched boundaries.** The recorded model-resident GridSFM component is shorter than the recorded AC construction-plus-solve component, but the current data do not support a formal cold end-to-end speedup claim.
